# Independent review, 2026-11-01

Before publishing, a separate AI reviewer was given the repo and asked to break it: find any way an agent or a rep could read or change what they should not, forge the audit trail, or get around autonomy, experiments or evidence rules. It ran each attack against a seeded database. Then it re-tested after the fixes.

The first pass confirmed eleven issues, two of them critical. All are fixed, and each one has a regression test in `tests/test_review_regressions.py`. The second pass confirmed the fixes, found four smaller gaps and one functional break, and those are fixed too.

## First pass

| # | Severity | Finding | Fix |
| --- | --- | --- | --- |
| 1 | Critical | Any signed-in user could call the internal `execute_field_update` with a forged decision row, changing any allowlisted field anywhere and attributing it to a real decision | It now takes a decision id, re-reads the row, and checks the caller made or approved it. Signed-in users can no longer call internal helpers except the ones row-level security needs (`0008_final_grants.sql`) |
| 2 | Critical | `apply_field_update` checked scope and evidence on one row id and updated the row named in the payload | Payload row must equal the checked row, and the decision subject must agree |
| 3 | High | An agent could mint "strong" evidence by choosing a strong kind, and cite evidence about a different record | Strong kinds from agents need a registered source that allows agent writes, otherwise they are stored weak and flagged. The strong evidence must be about the record being changed, or its company |
| 4 | Medium | The read-only user could read masked discount and margin values in the audit log | Masked columns never enter the audit log |
| 5 | Medium | An agent could hide a person's evidence by superseding it with itself | No self-supersede, newer rows only, and agents may supersede only agent-recorded evidence |
| 6 | Medium | Any rep could approve and activate plans for territories, partners and skills | Reviewing needs edit rights on the record. Territories, skills and loops need an owner. Partner plans need an owner or that partner's manager |
| 7 | Medium | Owners could edit a running experiment back to draft and reassign the holdout | Running experiments are frozen (only running to closed). Outcomes are written once. Level 4 audit samples are owner-only |
| 8 | Medium | Owners could relax the promotion bar and promote | Kept as the owner's call, but every change to the bar is audited and the rule in force is recorded with each promotion. Pay and process loops are capped at level 2 by a table constraint |
| 9 | Medium | An agent could label its own SMS as sent by a rep, or claim to be the partner, to get around policies | A touch sent as anyone but the agent always waits for that person |
| 10 | Low to medium | A rep could add deals and contacts to another territory's accounts, or move their own records between territories | Inserts and updates must land on accounts the caller can edit. Only owners change territory assignments |
| 11 | Medium | Deactivating a principal fell back to Atomic's admin flag and kept access | A principal row always wins. Inactive means no access |

## Second pass

| Finding | Fix |
| --- | --- |
| Renaming an agent's loop slipped past the pay-loop cap and running holdouts | An agent definition's loop can never change |
| Agents could supersede evidence written by the capture integration | Agents supersede only evidence that an agent recorded |
| A rep could move their own contact onto another territory's account | Contact updates must also land on an editable account |
| The service role lost execute on Atomic's search functions, which broke ledger writes from edge functions and ingest | Service role keeps execute on all public functions |
| Future internal helpers would be callable by everyone by default | Default privileges revoke execute in `ea_private` |

## Still open, by design or for later

- Internal lookup helpers that policies need (`company_owner_territory` and siblings) can reveal the owner and territory id of a record the caller cannot see. Low risk; fixing it means restructuring how child-table policies read their parent.
- Run records are self-reported: the agent states its own model and prompt version.
- With `agents_may_write = true` on a source (as in the demo seed), the strong-evidence rule trusts the agent's transcription. The safer production setup is for the capture integration to write first-hand evidence and agents to cite it.
- Atomic's own storage policies let any signed-in user read and delete attachments. Not changed here, because the shim cannot test storage.
- A rep can create an account whose address files it in another rep's territory. That is the territory rules working as written. Whether reps may create accounts outside their own territory is a policy choice.
